Investment Client Function Map

Every function an investment client can perform, what they put in, what comes back, which of those flows reach the advisor or super admin, and where the platform currently keeps the same fact in more than one place. Built from the code at commit 249d6ff.

1 · Organigram of client functions

Eight functional areas hang off the client account. Each leaf is one thing the client can do. The colour of the leaf's dot says who else touches that data: green is client-only, navy means the advisor writes it or reacts to it, outlined navy means the advisor can only read it, amber means it also depends on reference data the super admin maintains.

client-only data advisor writes it or is triggered by it advisor reads only depends on reference data the super admin maintains

2 · Functions: input, output, and who else is in the loop

One table per branch. "Advisor link" and "Super-admin link" say how the other role's actions connect to this function, not merely whether they could see it. The super admin bypasses every advisor-ownership check, so anything the advisor can do, the admin can do for any client; the column only lists what is specific to the admin.

writes advisor creates or changes the data reads advisor can only read it admin super-admin-specific dependency none no path to the other role today

3 · Source-of-truth map

The principle you applied in Coach Connect: every fact has exactly one owner, every screen reads it from that owner (directly or through one derived view), and nothing persists a second copy that can drift. Measured against that, the client area today keeps eleven facts in two or more places. The worst case is net worth, where five different numbers can be shown for the same client on the same day.

4 · Source-of-truth principles to adopt for tala

1. One owner table per fact

Each column in the schema has exactly one table that may be written for it. Write the owner next to the fact in the schema file comment and enforce it in code review. Profiles own identity and preferences; client_profiles own the relationship (advisor, status, stage, risk).

2. Derived values are computed, never stored

Net worth, portfolio value, goal funding, savings rate, pacing status and wealth score are functions of owner tables. They are returned by one server-side service each. The browser never sums and never writes a total back.

3. Snapshots are history, not source

net_worth_snapshots, goal_progress_snapshots and health_scores are written by a scheduled job from the service output, one row per user per day (unique index). Reads never fall back to them for the current value.

4. One vocabulary per state

Role, goal status, plan status, lead status, client status and onboarding stage are Postgres enums or CHECK constraints shared with Zod schemas in lib/db. A string that is not in the enum cannot be stored.

5. Relationships point one way

"Who is the advisor" is answered only by client_profiles.advisorId. Plans, conversations, tasks and ownership middleware resolve through it. Reassignment is one UPDATE plus one history row.

6. Ledgers over edited totals

Money movements (holding in/out, budget contributions, plan premiums) are append-only ledger rows. Balances and monthly contribution lists are queries over the ledger. This replaces the contributions JSON and the manual balance arithmetic.

7. Reference data has one admin door

Prices, benchmarks, strategy returns and the fund catalogue are written only by server jobs or super_admin routes. Advisors and client requests read them; they never create cache rows.

8. One tier model, feature-flagged

Free and client tiers share the same tables (goals, budget, net worth, score). Tier only changes limits and which screens are offered, so promotion from free to client carries every number across with no migration.

9. Legacy is read-only, then gone

packages, portfolio_holdings, scenarios v1, kyc_documents, client_financial_snapshots and budget_entries get an export, a cut-over date, and then a drop. Until then, no new code path may read them.

5 · Migration order (safe sequence)

  1. Enums and constraints first. Add CHECK constraints for role, goal status, plan status, lead status, client status; add unique indexes on (user, month) for budget, (user, date) for snapshots and scores. This surfaces existing bad rows before any logic moves.
  2. Net worth service. Implement GET /client/networth/summary server-side with the formula the net worth page uses today (holdings + plans + assets − mortgages − liabilities, live prices). Point the dashboard ring, Sol tool, wealth score and advisor/admin lists at it. Stop the browser POST of snapshots; add a nightly job.
  3. Goal funding. Return computed funding and pacing on GET /goals; delete the browser copy in useGoals; block auto-update and pathway upsert for goals that have links or belong to an investment client.
  4. Advisor pointer. Add advisor_assignments history; drop advisorId from financial_plans and conversations in favour of a join; rewrite the ownership middleware to resolve through client_profiles only; take advisorId out of the review-request body.
  5. Profile fields. Collapse preferredDisplayCurrency into profiles.preferredCurrency, riskProfile into client_profiles with a source column, five onboarding flags into one stage enum. Update the onboarding screens and the currency toggle in the same change.
  6. Ledgers. Introduce a plan-contribution ledger; replace investmentContributions JSON with a query; recompute month totals from ledgers; remove the hand-written balance updates.
  7. Scores and scenarios. One scoring service with a tier column; add the advisor "push scenario" route; drop the v1 scenarios table.
  8. Prices and KYC. Server-fed prices table with provider and timestamp; documents as the only document table with derived kycStatus.
  9. Retire legacy. Export, cut over, drop client_packages, portfolio_holdings, kyc_documents, client_financial_snapshots, budget_entries.
Each step is independently shippable and testable against the existing supertest harness. Steps 2 to 4 also close security findings F-2, F-3, F-17, F-20 and F-24 from the audit, so they are worth doing before the UI redesign rather than after.
