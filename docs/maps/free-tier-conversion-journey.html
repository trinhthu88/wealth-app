Free Tier Conversion Journey

Design for the free tier as a channel into the investment-client product: the same feature tree, the same tables, the same screens, with tier gates instead of a separate app, and conversion checkpoints placed where the user's own data shows they are ready. Nothing here needs a new data model that the client plan does not already call for.

1 · One product, three rungs

The current code already contains two products glued together: a free planner (pathway, budget_entries, one goal, health score) and a client portal (onboarding, client_budget_months, unlimited goals, wealth score). The proposal collapses them. A free user is a Track B client without an advisor and with limits. A Track B client is a free user plus an advisor. A Track A client is a Track B client plus an advised plan. Each rung unlocks by changing one field, not by moving data.

Why this is cheaper than it looks. The client tier already contains five Track B → Track A conversion components (surplus CTA, bring-under-management compare, goal scenario CTA, Track B conversion CTA, dashboard conversion section). The free tier needs the same components with a different destination: "talk to an advisor" instead of "message your advisor". One checkpoint engine serves both rungs.

2 · The journey with conversion checkpoints

Checkpoints are not banners. Each one fires on the server when the user's own data crosses a threshold, records that it fired, and offers one specific thing an advisor could do with that data. The diamonds below are those moments. The lower lanes show what happens on the tala side once the user accepts one.

Rules that keep checkpoints from becoming nagging. One visible checkpoint at a time, priority C7 < C1 < C6 < C4 < C3 < C5 < C2 (most data-specific wins). A fired checkpoint is recorded with the data snapshot that triggered it. Dismissal is a server fact with a 30-day cool-down, not a localStorage flag. Accepting any checkpoint creates one lead per user (re-touched, never duplicated) and suppresses all others until that lead is churned, cold, or converted.

7 · Engine and source of truth

Three small pieces, all server-side, all reading the owner tables from the client source-of-truth plan. The browser never decides a gate, never fires a checkpoint, and never stores a dismissal.

7.1 Source-of-truth rules specific to the funnel

Tier is derived, never stored twice

Tier = f(profiles.role, client_profiles.clientTrack). No "isFree" flags, no tier columns on feature tables. The pathway wizard, budget_entries and the free health-score formula are deleted because they encoded tier as separate code paths.

Limits live in one file

TIER_LIMITS is imported by requireAllowance on the server and serialised into /me/entitlements for the UI. Changing a number is one commit and takes effect in both places.

Checkpoints are records

conversion_checkpoints is the only memory of what was shown, dismissed or accepted. It replaces the four localStorage dismissal keys and makes funnel analytics a query.

One lead per user

The lead row is the funnel record. Name, email, score and risk profile are read through the userId join, never copied. Source is the checkpoint code, so the advisor sees why.

Promotion moves nothing

PUT /leads/:id status client flips role and sets advisorId. Goals, holdings, budget months, snapshots, scores and engagement are already in the client tables. The onboarding bridge and dashboard backfill are deleted.

Engagement is a server fact

Streak, milestones and tips move to a user_engagement table written by the same write hooks the evaluator uses. The advisor's lead view shows it; C6 reads it.

8.3 Build order

  1. Tier policy and entitlements. One file, one guard, one endpoint. Wire the existing goal cap through it so the Add button and the API agree. Closes audit finding F-5 as a side effect.
  2. Open the client screens to free users behind entitlements; retire the free pages one by one (goals, net worth, dashboard first; budget after the table migration).
  3. Direct ask everywhere (C7). Replace mailto and /book; add the conversion-state advisor card driven by lead status; unlock messages and documents for assigned leads.
  4. Checkpoint evaluator with C2, C4, C5 first (they have the clearest data signals and existing components), then C3, C1, C6.
  5. Engagement table and the advisor lead view as read-only client screens, including fired checkpoints.
  6. Budget unification (shared with the client source-of-truth plan), then delete the pathway, budget_entries and the free score formula.
  7. Track A checkpoints (C8–C10) re-pointed at the same engine; measure both rungs with the same queries.
Steps 1 to 3 give a measurable funnel in a few weeks without touching the data model. Steps 4 to 6 are shared with the investment-client source-of-truth migration and should be scheduled together.
