Free User Function Map

The free user is tala's top of funnel: a self-service planner whose job is to build a habit, produce a health score, and hand a warm lead to an advisor. This page maps that journey, every function the free user can perform with its inputs and outputs, where the super admin and advisor touch it, and where the same fact is kept in more than one place. Built from the code at commit 249d6ff.

1 · Journey from visitor to client, with the handoffs

Unlike the investment client, the free user's data model is shaped by a lifecycle that crosses three roles. The super admin assigns the lead, the advisor promotes it, and at that moment some of what the free user built carries over and some is stranded. The diagram shows the seven stages, who acts at each, and what data crosses the promotion line.

Tier boundary is not a data fact today. Role is the only thing that separates a free user from a client, and only the one-goal cap checks it. Any source-of-truth design for the free tier has to assume the same tables serve both tiers, which is also the simplest way to make promotion lossless.

5 · Recommendations for the free-user architecture

1. Same tables for both tiers

Goals, assets, liabilities and budget already share tables except for budget. Move the free budget onto client_budget_months and the free score onto the shared scoring service, and promotion becomes a role flip with nothing to migrate and nothing stranded.

2. Pathway writes owners, stores status

Each step becomes a form bound to the owner table it edits. pathway_progress keeps step, status and completedAt. The dashboard backfill and the client-onboarding bridge are deleted because they no longer have anything to bridge.

3. One tier policy module

Limits (one goal, locked slot, which pages) live in one server module that both the API and the UI ask. The Add button is disabled from the same answer that makes the API return 403, so the user never sees a generic failure.

4. Role check on the client tier

Until the tiers truly share one model, put requireRole on the /client, scenarios, packages, portfolio and plan routers so the free user's real capability set equals the free UI (closes F-5).

5. Engagement is a server fact

Streak, milestones and tip history move to a user_engagement table. The advisor's lead view gains an engagement panel, which is the signal they most need to prioritise leads, and the free user keeps their badges across devices and across promotion.

6. One upgrade action

All upgrade controls call the interest action with a source value. Add a lightweight "we have passed you to an advisor" state on the free dashboard, driven by the lead status, so the user sees something happen after they raise their hand.

7. Lead reads the profile, never copies it

For linked leads, name, email, score and risk profile come through the userId join. The lead row is the funnel record only. This also removes the never-used quizResult column or gives it a real producer.

8. Computed values are never written

Goal growth, goal status, net worth and savings rate are computed on read by the shared goal-math and net worth services. Remove POST /goals/auto-update and the stored projection status.

9. Fix the two dead ends first

Transaction edit calls a route that does not exist, and three upgrade links go to /book which is a 404. Both are small changes with immediate user impact and should ship before any restructuring.

6 · Migration order (safe sequence)

  1. Quick fixes. Add PUT /budget/transactions/:id; replace /book and the mailto with the interest action; disable the Add-goal button at the cap. No schema change.
  2. Role guard. requireRole("investment_client","super_admin") on the client routers; stop GET /client-profile/me from creating rows. Closes F-5 and defines the free capability set.
  3. Constraints. Unique (user, month) on budget tables, unique (user, date) on health_scores, CHECK on goal status. Surfaces duplicates created by the pathway before logic moves.
  4. Scoring service. One service with a tier column; free and client GET become reads; recalculation replaces today's row. Fix the "Score 70+" milestone to read it.
  5. Pathway rewrite. Steps bound to owner tables; formData dropped after a one-off backfill of any owner row that is still empty; delete the dashboard backfill and the client-onboarding bridge; upsert-by-name replaced by id-based updates.
  6. Budget unification. Migrate budget_entries into client_budget_months (free fields as a subset) and budget_transactions into the ledger; point free pages at the client budget routes behind the tier policy.
  7. Goal math. Remove auto-update and stored projection status; one computeGoalProgress for both tiers; pacing derived on read.
  8. Engagement table. user_engagement with streak, milestones, tip history; browser becomes a cache; advisor lead view shows it.
  9. Lead normalisation. Profile fields through the join for linked leads; drop the copied columns or restrict them to anonymous leads; remove or implement quizResult.
Steps 1 to 3 are a week of work and remove the most visible defects. Steps 4 to 7 are the same services the investment-client plan needs, so they should be built once and shared rather than done per tier.
